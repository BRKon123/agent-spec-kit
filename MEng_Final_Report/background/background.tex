\label{chap:background}

\section{From Language Models to Agentic Systems}
\label{sec:bg-llms-to-agents}

Modern large language models are built on the Transformer architecture, introduced by Vaswani et al. as a sequence model based on attention rather than recurrence or convolution \cite{vaswani2017attention}. Scaling this architecture produced models that can interpret natural-language instructions, generate structured text, and retain conversational context. Brown et al. showed that sufficiently large pretrained models can perform many tasks through in-context learning rather than task-specific gradient updates \cite{brown2020language}; instruction tuning and reinforcement learning from human feedback subsequently made these models more useful as general-purpose assistants \cite{ouyang2022training}.

Prompting research also showed that model behaviour depends strongly on how a task is framed. Few-shot examples can define a task through demonstrations \cite{brown2020language}, while chain-of-thought and zero-shot reasoning prompts can change how models decompose problems \cite{wei2022chain,kojima2022large}. Self-consistency exploits the fact that repeated samples may follow different reasoning paths \cite{wang2022self}. For evaluation, the important conclusion is not the details of each prompting method, but that LLM behaviour is probabilistic and prompt-sensitive: one successful execution does not establish that a system will behave reliably across repeated trials.

As LLMs were incorporated into applications, the unit of behaviour expanded beyond a single generated answer. Retrieval-augmented generation combines retrieval, context selection, and generation \cite{lewis2020retrieval}; a failure may arise because the wrong material was retrieved, because relevant evidence was ignored, or because the answer was unsupported. Tool-using agents add another layer. ReAct introduced a pattern in which an LLM alternates between reasoning, executable actions, and environment observations \cite{yao2023react}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.88\textwidth]{figures/react_prompting.png}
  \caption{ReAct interleaves natural-language reasoning with executable actions and environment observations \cite{yao2023react}.}
  \label{fig:react-prompting}
\end{figure}

Toolformer explored models that decide when and how to call external tools \cite{schick2023toolformer}, while Gorilla focused on selecting APIs from large collections \cite{patil2023gorilla}. These systems make the execution trace a first-class artefact: behaviour includes an ordered sequence of tool calls, arguments, observations, and state changes, not only the final paragraph shown to the user.

This transition changes the reliability question. A conventional language benchmark asks whether a model produced an acceptable answer. A tool-using agent evaluation must also ask whether the system selected appropriate actions, respected policy constraints, interpreted observations correctly, and achieved the intended effect in its environment. The rest of this chapter reviews the failure modes, benchmarks, and software-testing ideas that motivate this broader view.

\section{Failure Modes in Tool-Using LLM Agents}
\label{sec:bg-agent-failures}

Hallucination in an agent can affect more than the final wording. A system may invent the contents of a tool result, assume that an action succeeded, or continue from a state the environment never reached. Since later steps depend on earlier observations, one unsupported assumption can propagate through an entire trajectory and become difficult to diagnose from the final response alone.

Tool use introduces additional failure classes. An agent may select the wrong tool, construct an invalid or semantically wrong argument, call otherwise correct tools in the wrong order, or act when it should ask for clarification or abstain. Function-calling benchmarks such as BFCL explicitly include relevance detection, abstention, and multi-step calls \cite{patil2025bfcl}. ToolEmu shows that selecting a plausible tool is not sufficient when arguments are fabricated, unsafe, or misaligned with the instruction \cite{ruan2024toolemu}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{figures/tool_emu_failure_examples.png}
  \caption{Typical failures of LM agents in ToolEmu \cite{ruan2024toolemu}, including fabricated assumptions, instruction misinterpretation, unsafe execution, and risk ignorance.}
  \label{fig:toolemu-failures}
\end{figure}

Multi-turn interaction makes these issues more pronounced. AgentBench evaluates agents across several interactive environments and identifies long-term reasoning and instruction following as major obstacles \cite{liu2023agentbench}. MINT similarly shows that single-turn ability does not necessarily transfer to interactions in which the system must update its plan after feedback \cite{wang2023mint}. An agent must remember earlier constraints, distinguish corrected information from stale information, and maintain consistent bindings between user entities and tool arguments.

Security work adds a related concern. Agents that browse, retrieve documents, or process user-provided files must distinguish trusted instructions from untrusted content. Greshake et al. show that indirect prompt injection can redirect LLM-integrated applications through instructions embedded in external data \cite{greshake2023not}. A response may therefore appear fluent and relevant while the system has violated an instruction hierarchy, exposed protected information, or performed an unsafe action.

A further difficulty is non-determinism. Even with the same prompt and tools, stochastic decoding and small contextual differences may produce different trajectories. A system that succeeds once but fails under repeated runs may be unsuitable for deployment. Metrics such as \textit{pass}$^k$ in $\tau$-bench address this by measuring consistent success across repeated attempts \cite{yao2024taubench}.

These failures can be organised into three related notions of correctness. \emph{Answer correctness} concerns what the user sees. \emph{Trajectory correctness} concerns the sequence of decisions, tool calls, and observations. \emph{State correctness} concerns the environment after execution. They can diverge: a support agent may produce a reassuring reply while skipping authentication, writing to the wrong account, or failing to perform the promised action. Conversely, imperfect wording may accompany operationally correct behaviour. This distinction motivates evaluation that preserves the conversation, trace, and resulting state.

The practical importance of this distinction increases when actions have side effects. An incorrect sentence can often be corrected on the next turn, but a wrong database update, message, order, or payment may persist. Agent evaluation must therefore check not only task completion, but also required preconditions, unwanted side effects, and whether the system should have abstained.

\section{General LLM Evaluation and Its Limits}
\label{sec:bg-general-eval}

General language-model benchmarks provide standardised comparisons of knowledge, reasoning, and language understanding. MMLU, for example, measures performance across many academic and professional domains \cite{hendrycks2021mmlu}. HELM broadened evaluation from a single accuracy score to a coverage problem across scenarios and dimensions such as robustness, calibration, fairness, toxicity, and efficiency \cite{liang2022helm}. These benchmarks make model-level progress visible and reproducible, but they usually operate on fixed inputs and final outputs rather than an executable environment.

Open-ended generation also makes strict reference-based metrics less adequate. Exact match, BLEU, and ROUGE assume that good responses resemble a reference, even though many valid answers may use different wording. LLM-as-a-judge methods instead use a strong model to apply natural-language criteria. G-Eval reports higher correlation with human judgement than many traditional metrics \cite{liu2023geval}; MT-Bench and Chatbot Arena popularised model-based pairwise comparison while also documenting biases in judge behaviour \cite{zheng2023judging}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.76\textwidth]{figures/geval_pipeline.png}
  \caption{G-Eval applies a rubric-driven LLM judge and aggregates the model's probability over rating levels \cite{liu2023geval}.}
  \label{fig:geval-pipeline}
\end{figure}

These methods scale more easily than human review and are useful for qualities such as relevance, tone, completeness, or helpfulness. However, a model judge may not reliably establish whether a particular tool was called, whether an argument matched a schema, or whether a database changed correctly. It may also reward verbose explanations that sound plausible. In an agent evaluation, an LLM judge is therefore one possible oracle rather than a substitute for executable checks.

RAG evaluation frameworks illustrate a more component-oriented approach. RAGAS separates dimensions such as context relevance, faithfulness, and answer relevance \cite{es2023ragas}; ARES combines synthetic data, lightweight judges, and a small amount of human annotation \cite{saadfalcon2023ares}. These approaches recognise that a pipeline should be evaluated at the level of its components and evidence flow. Nevertheless, RAG systems typically retrieve and generate, whereas agents may interact over several turns, use multiple tools, and cause persistent side effects.

Scalar metrics remain valuable for ranking systems, comparing experiments, and tracking regressions. Their limitation is diagnostic: a single score rarely identifies whether a failure arose in instruction interpretation, tool choice, argument construction, observation handling, response generation, or state mutation. Aggregate results should therefore be backed by inspectable traces and assertion-level evidence. The granularity of the oracle should match the claim: conversational quality can be judged semantically, while precise tool and state claims call for deterministic or executable validation.

\section{Tool-Use and Function-Calling Benchmarks}
\label{sec:bg-tool-benchmarks}

The first wave of tool-use benchmarks focused on mapping natural-language requests to API calls. API-Bank introduced dialogue tasks involving intent understanding, API selection, and correct call generation \cite{li2023apibank}. ToolLLM and ToolBench expanded the setting to more than 16,000 real-world APIs and included both single- and multi-tool instructions \cite{qin2023toollm}. These benchmarks made the interface between models and software explicit: a generated call must satisfy machine-readable constraints as well as the user's request.

Large API spaces also complicate evaluation. A call can be syntactically valid yet semantically inappropriate, while a partially correct chain may still fail the user's goal. StableToolBench highlights an additional reproducibility issue: benchmarks that depend on live APIs can change because services fail, return different data, or become unavailable \cite{guo2024stabletoolbench}. Its virtual API server illustrates the importance of controlling the environment so that changes in results can be attributed to the agent rather than external noise.

BFCL provides a systematic view of function-calling capabilities, including function selection, relevance detection, AST-based argument checking, executable calls, parallel calls, multi-turn interactions, and agentic scenarios \cite{patil2025bfcl}. Its contribution is to make tool correctness precise. Evaluation may need to consider the function name, required and optional arguments, types and values, call order, number of calls, and whether the model should have abstained.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.70\textwidth]{figures/ast_based_function_evaluation.png}
  \caption{BFCL parses generated function calls and checks names, parameters, types, and values against the reference \cite{patil2025bfcl}.}
  \label{fig:bfcl-ast-eval}
\end{figure}

Function-calling benchmarks nevertheless cover only part of a complete episode. Real tasks may require the agent to obtain missing information, interpret tool results, perform several dependent actions, and validate persistent effects. An isolated correct call does not show that the surrounding conversation or resulting state is correct.

These benchmarks also motivate trace normalisation. Agent frameworks may represent tool use as chat messages, JSON objects, callback events, or framework-specific spans. Evaluation tied directly to one representation becomes fragile. A normalised trace can instead expose stable semantic fields such as tool name, arguments, result, order, and parent-child relationship. Assertions then target behaviour rather than incidental framework details.

\section{Executable and Stateful Agent Benchmarks}
\label{sec:bg-stateful-benchmarks}

Executable benchmarks shift the unit of evaluation from a generated answer to an episode in an environment. AgentBench evaluates multi-step reasoning, decision-making, and instruction following across several interactive domains \cite{liu2023agentbench}. WebArena uses self-hosted websites and programmatic validators so that success depends on the resulting website state, not an agent's statement that the task was completed \cite{zhou2023webarena}. SWE-bench applies the same principle to software engineering: a generated patch is judged by whether it resolves an issue and passes tests in the repository \cite{jimenez2024swebench}.

Planning benchmarks provide a complementary view. PlanBench studies whether models can reason about preconditions, effects, and goal states \cite{valmeekam2023planbench}. These concepts appear implicitly in tool-using agents: a missing prerequisite, impossible call, or incorrect assumption about state can invalidate the remainder of a trajectory.

AppWorld is particularly relevant to stateful evaluation. It provides simulated applications and hundreds of APIs, then uses programmatic tests over initial and final state to verify task completion \cite{trivedi2024appworld}. It also checks for collateral damage, recognising that an agent should not achieve the main goal through unrelated or harmful changes.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.86\textwidth]{figures/app_world_engine_and_benchmark.png}
  \caption{AppWorld uses simulated applications and programmatic tests over initial and final state \cite{trivedi2024appworld}.}
  \label{fig:appworld-engine}
\end{figure}

$\tau$-bench combines simulated users, domain policies, database-backed tools, final-state validation, and repeated trials in realistic retail and airline tasks \cite{yao2024taubench}. Its design captures several properties of deployed domain agents: success depends jointly on conversation, policy compliance, tool use, and state, while reliability depends on repeated performance.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.88\textwidth]{figures/tao_bench_setup.png}
  \caption{$\tau$-bench combines a simulated user, a policy-guided agent, and database-backed tools; success is determined from the resulting environment state rather than the final reply alone \cite{yao2024taubench}.}
  \label{fig:taubench-setup}
\end{figure}

ToolSandbox extends this direction with stateful tool execution, implicit dependencies, on-policy user simulation, and milestone-based evaluation \cite{lu2024toolsandbox}. Milestones expose whether required intermediate conditions were satisfied, which is useful when final-state success could conceal unsafe or incomplete behaviour.

Together, these systems show a progression from static output grading to executable, stateful, interactive, and repeated evaluation. They demonstrate why traces and state matter, but they are primarily fixed research environments. A team still needs reusable infrastructure for expressing its own conversations, policies, tool expectations, and postconditions. That gap motivates the framework developed in this project.

\section{Test Oracles, Specifications and Structured Evidence}
\label{sec:bg-oracles}

The software-testing literature provides useful language for this problem. A test oracle is a mechanism for deciding whether observed behaviour is correct. Barr et al. identify the oracle problem as central to testing: generating inputs is not sufficient if there is no reliable way to determine whether the result is right \cite{barr2015oracle}. LLM systems intensify the problem because outputs are open-ended, context-dependent, and often partially correct. Strict string comparison may be too brittle, while an unconstrained natural-language judgement may be too vague.

For an agent, there is rarely one universal oracle. Different surfaces require different checks: semantic criteria for a final response, schemas for structured output, names and arguments for tool calls, ordering constraints for trajectories, and invariants or postconditions for environment state. Table~\ref{tab:agent-oracle-types} summarises representative examples.

Structured evidence makes these checks useful for debugging. A scenario-level failure without further detail still requires the developer to reconstruct the interaction manually. A diagnostic counterexample should instead identify the broken expectation, the relevant turn or trace location, and the expected and actual values. The location may be a tool call, a nested argument path, a message, or a state postcondition.

LLM judges complement rather than replace deterministic oracles. They are useful for subjective qualities that are difficult to encode, but precise machine-level claims are better handled by structured matchers and executable checks. A judge may assess whether a response is empathetic; it should not be the only evidence that a JSON field matched its schema or that a database row was updated correctly.

Metamorphic testing supplies another useful idea for cases where exact outputs are difficult to specify. It checks relations across multiple executions rather than a single reference result \cite{chen1998metamorphic}. For an agent, harmless paraphrases should often preserve the intended action, irrelevant context should not alter a decision, and semantically equivalent tool observations should lead to compatible behaviour. Such relations define robustness properties without requiring one exact transcript.

\section{Property-Based Testing, Fuzzing and Shrinking}
\label{sec:bg-testing-lineage}

Property-based testing is a natural predecessor for generative agent evaluation. QuickCheck separates generation from checking: a developer specifies properties, the system explores many generated inputs, and failures are returned as counterexamples \cite{claessen2000quickcheck}. This is useful when manually enumerating all relevant cases is impractical. Agent interactions have the same difficulty because the space of user phrasings, dialogue paths, observations, and edge cases is too large for a fixed set of hand-written scripts.

The separation between generation and checking is essential. Diverse conversations are not tests unless they are paired with oracles. A generated interaction becomes useful when it is checked against requirements such as required tool use, forbidden side effects, policy compliance, or acceptable final responses. Otherwise, generation produces transcripts but no justified correctness signal.

Shrinking is the companion idea. QuickCheck reduces failing values, while Delta Debugging formalises the broader task of simplifying failure-inducing inputs without removing the failure \cite{zeller2002simplifying}. A smaller counterexample reduces debugging effort by excluding irrelevant material. For an agent, however, the input is an interactive trajectory rather than a single value. Removing one turn may change every subsequent response, so a shrinker must preserve the same diagnostic failure rather than merely producing any shorter failing conversation.

Fuzzing contributes systematic variation. Traditional fuzzers mutate inputs to discover crashes or unexpected behaviour. LLM-specific work adapts this idea to prompts and safety failures. GPTFuzzer uses seed prompts, mutation operators, and a judgement model to generate jailbreak prompts \cite{yu2023gptfuzzer}. FuzzLLM combines structured attack templates, constraints, policy-violating questions, and a label-model oracle \cite{yao2023fuzzllm}.

  \centering
  \includegraphics[width=0.90\textwidth]{figures/fuzz_llm_pipeline.png}
  \caption{FuzzLLM combines seed templates, structured mutations, execution against a target model, and an automated oracle \cite{yao2023fuzzllm}.}
  \label{fig:fuzzllm-pipeline}
\end{figure}

Although these systems focus on red teaming, their general pattern (seed cases, structured mutation, repeated execution, and an oracle) extends to domain-specific agent testing. The predicate is broader than whether disallowed content was produced. A generated conversation may reveal a wrong tool, stale identifier, missing clarification, unsafe action, or incorrect state transition.

Generation must also remain within the domain. Unconstrained messages are often unrealistic, whereas overly narrow variation simply reproduces the manual examples already known. Structured personas, omitted facts, ambiguity, corrections, conflicting requests, and plausible adversarial behaviour provide ways to widen the search while retaining task relevance.

Regression testing completes the workflow. Once a useful failure is found and understood, it should become a stable scenario that can be rerun after changes to prompts, models, tools, or orchestration code. Since LLM outputs are stochastic, a regression should preserve the behavioural condition that matters rather than every token of the original transcript. This project adopts that generate, check, shrink, and preserve lineage for conversational, tool-using agents.
