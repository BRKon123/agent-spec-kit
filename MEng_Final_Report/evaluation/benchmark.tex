\section{TelcoSupportBench}
\label{sec:telcosupportbench}

TelcoSupportBench models a mobile-network customer-support desk. A reference agent can authenticate customers, inspect lines, run nested network and billing specialists, open tickets, apply credits, and mutate a permissive SQLite store. Correctness is defined by executable scenarios: each task specifies a scripted customer dialogue and explicit checks over the assistant's replies, the tool trace, and the final store state. This is closer to integration testing than to scoring a single final answer, and it differs from fixed leaderboard benchmarks such as $\tau$-bench or AppWorld, where task orchestration and environment code are bundled with the benchmark rather than expressed as reusable scenario tests on a developer's own agent \cite{yao2024taubench,trivedi2024appworld}.

The rest of this section introduces the task catalogue and oracle lanes, then reports how the reference agent performed on an initial full run before the expressiveness, fault-injection, and generative studies later in the chapter.

\subsection{Oracle lanes}

Each of the fifty tasks is exercised through four scenario variants that share the \emph{same} user messages and differ only in which assertions run. The lanes are output (O), state (S), trace (T), and full (F).

Agent bugs do not always show up in the same place. A reply can pass a rubric while a tool is invoked with the wrong arguments; trace checks can fail while the customer-facing answer still sounds reasonable; store oracles can catch policy violations in application state that the reply never mentions. Splitting checks into lanes lets the evaluation compare how well each \emph{type} of assertion finds problems on the same dialogue: output-only scenarios approximate grading the final answer; trace and state lanes target tool choreography and side effects; the full lane (F) is the combined regression developers would run in practice. Later in the chapter, the fault-injection study (Section~\ref{sec:fault-detection}) reuses this split to measure which lanes catch injected faults and which miss them when only one surface is checked.

Table~\ref{tab:oracle-lanes} maps each lane to the surface it inspects; the full scenario combines every check from the other three lanes at the same turn positions in the dialogue.

\begin{table}[htbp]
\centering
\caption{Oracle lanes on TelcoSupportBench. The same scripted dialogue is used in all four variants; only the checks differ.}
\label{tab:oracle-lanes}
\begin{tabular}{@{}llp{6.8cm}@{}}
\toprule
Lane & Surface & Typical assertions \\
\midrule
O & User-facing reply after each user turn & \texttt{assert\_output}, \texttt{m.llm\_criteria} rubrics \\

The baseline run below already illustrates the gap: output checks pass on every task, while trace and state lanes fail on many of the same conversations. That pattern motivates treating lane choice as part of test design, not only as an implementation detail.

Output checks pass on every task in this run: the agent's replies satisfy the rubrics when those are the only assertions enabled. Failures concentrate on trace, state, and full scenarios rather than on output alone. Twenty-seven tasks fail on at least one lane; common patterns are missing audit notes in the store, wrong tool order or line binding in the trace, state mutations that violate policy, and combined failures on long-horizon dialogues. Listing~\ref{lst:baseline-failure-audit} shows the counterexample box for one state-lane failure (task T21): the oracle names the violated rule, and the event trace shows that a credit was applied without the required audit note.
