\section{Summary}
\label{sec:evaluation-summary}

This chapter evaluated how well \emph{agent-spec-kit} surfaces multi-faceted agent errors and compared it as a whole against seven other evaluation approaches on TelcoSupportBench. The focus was whether this library gives agent developers a clearer way to write and run behavioural tests, then learn from the failures they surface. Competing tools can grade final answers and, with enough custom code, inspect tools or application state, but that work is usually split across scorers, helpers, transforms, and provider wiring. \emph{agent-spec-kit} treats reply, tool trace, and store as first-class surfaces in one scenario language, with failure messages and discovery workflows aimed at the same developer loop.

The baseline run on the reference agent illustrated why that breadth matters. One hundred and forty-six of two hundred oracle slots passed, yet failures clustered on trace, state, and full lanes: the agent could sound reasonable while tool ordering was wrong, an argument was bound incorrectly, or a store update never happened. That is one reason a library built only around answer grading is not enough, even when other stacks can technically reach deeper checks if you invest in glue code.

The expressiveness study made the library comparison concrete across twelve check patterns and eight frameworks (pytest, LangSmith, Pydantic Evals, Promptfoo, Braintrust, Ragas, and DeepEval). Checks written in the scenario language read as a short script: customer turns, tool expectations, output rubrics, and state assertions in sequence, without jumping between files to learn what is being tested. \emph{agent-spec-kit} totals 165 lines of check logic and scores \textbf{A} on authoring clarity for all twelve specimens; metric-oriented libraries total more when each check carries its own trace parsing, evaluator class, and test-case construction---DeepEval and Pydantic Evals reach 496 and 532 lines respectively. When examples are meant to fail, built-in matchers usually name the check, where it fired, and what differed; reimplementations in pytest and commercial-style libraries often stop at \texttt{AssertionError} or a zero score, while Ragas built-in tool metrics sometimes return only a scalar and DeepEval surfaces longer natural-language reasons from \texttt{ToolCorrectnessMetric} and \texttt{JsonCorrectnessMetric}. That specificity matters in day-to-day work: the developer sees which tool, field, or store fact broke, not only that something failed, which shortens the loop from red test to fix.

The fault-injection study carried that into regression testing. On baseline-passing task-and-lane pairs, the full checks \emph{agent-spec-kit} expresses caught most injected ordering and binding faults, along with side effects that should not have occurred; narrower lanes missed several of the same injections. Richer checks are what stop an agent change from silently breaking tool choreography or environment invariants while the reply still sounds fine. When those checks fail, structured counterexamples rather than opaque booleans let a developer see what broke and fix it quickly, which is how teams keep agents reliable as prompts or tool wiring change.

Discovery studies extended the same idea beyond fixed scripts. Manual dialogues give a stable regression backbone, but simulated users and mutation operators surfaced many distinct failure signatures and tool paths the canonical scripts never exercised. Regression extraction then pinned captured sim failures as permanent scenario files with the same F-oracles, so a finding from exploration can re-enter the suite without rewriting the whole test by hand. Fuzzing and simulation widen the search space so bugs appear in customer wordings and trajectories a human author might not have written, while the same expressive oracles judge whether the agent still respects policy.

\subsection{Limitations}
\label{sec:evaluation-limitations}

All generative arms used the same small model for judges and simulated users; results may change with stronger models or lower temperature. Only one reference agent and one telecom domain were studied, so the figures describe this setup rather than customer-support agents in general. LLM criteria in output and full lanes make some failures judge-dependent. Regression extraction generated a valid file for every eligible failure, but signature-stable rerun remains an open workflow concern: discovery should treat repeats and failure identity as first-class, as argued in the methodology chapter.
