\section{Summary}
\label{sec:evaluation-summary}

This chapter evaluated how well \emph{agent-spec-kit} surfaces multi-faceted agent errors and compared it as a whole against five other evaluation approaches on TelcoSupportBench. The focus was whether this library gives agent developers a clearer way to write, run, and learn from behavioural tests. Competing tools can grade final answers and, with enough custom code, inspect tools or application state, but that work is usually split across scorers, helpers, transforms, and provider wiring. \emph{agent-spec-kit} treats reply, tool trace, and store as first-class surfaces in one scenario language, with failure messages and discovery workflows aimed at the same developer loop.

The baseline run on the reference agent illustrated why that breadth matters. One hundred and forty-six of two hundred oracle slots passed, yet failures clustered on trace, state, and full lanes: the agent could sound reasonable while tool ordering, argument binding, or a store update was wrong. That is one reason a library built only around answer grading is not enough, even when other stacks can technically reach deeper checks if you invest in glue code.

The expressiveness study made the library comparison concrete across twelve check patterns and six frameworks. Checks written in the scenario language read as a short script: customer turns, tool expectations, output rubrics, and state assertions in sequence, without jumping between files to learn what is being tested. Line counts are competitive even though each specimen counts that whole scenario, not just an isolated scorer body. When examples are meant to fail, built-in matchers usually name the check, where it fired, and what differed; reimplementations in pytest and commercial-style libraries often stop at \texttt{AssertionError} or a zero score. That specificity matters in day-to-day work: the developer sees which tool, field, or store fact broke, not only that something failed, which shortens the loop from red test to fix.

The fault-injection study carried that into regression testing. On baseline-passing task-and-lane pairs, the full checks \emph{agent-spec-kit} expresses caught most injected ordering, binding, and side-effect faults; narrower lanes missed several of the same injections. Richer checks are what stop an agent change from silently breaking tool choreography or environment invariants while the reply still sounds fine. When those checks fail, structured counterexamples rather than opaque booleans let a developer see what broke and fix it quickly, which is how teams keep agents reliable as prompts, models, and tools change.

Discovery studies extended the same idea beyond fixed scripts. Manual dialogues give a stable regression backbone, but simulated users and mutation operators surfaced many distinct failure signatures and tool paths the canonical scripts never exercised. Regression extraction then pinned captured sim failures as permanent scenario files with the same F-oracles, so a finding from exploration can re-enter the suite without rewriting the whole test by hand. Fuzzing and simulation widen the search space so bugs appear in customer wordings and trajectories a human author might not have written, while the same expressive oracles judge whether the agent still respects policy.

\subsection{Limitations}
\label{sec:evaluation-limitations}

All generative arms used the same small model for judges and simulated users; results may change with stronger models or lower temperature. Only one reference agent and one telecom domain were studied, so the figures describe this setup rather than customer-support agents in general. LLM criteria in output and full lanes make some failures judge-dependent. Regression extraction generated a valid file for every eligible failure, but signature-stable rerun remains an open workflow concern: discovery should treat repeats and failure identity as first-class, as argued in the methodology chapter.
