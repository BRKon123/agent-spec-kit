\section{Summary}
\label{sec:evaluation-summary}

This chapter evaluated how well \emph{agent-spec-kit} detects failures across replies, tool traces, and application state. It also compared the framework with seven other evaluation approaches across the full TelcoSupportBench suite.

The baseline results showed why these three surfaces must be tested together. The reference agent passed 146 of 200 oracle slots, but most failures appeared in the trace, state, and full lanes. In several cases, the final reply sounded correct even though a tool was called in the wrong order, an argument was incorrect, or the expected store update did not occur. Output-only grading would therefore have missed important errors.

The expressiveness study compared twelve check patterns across \emph{agent-spec-kit} and seven alternatives. \emph{agent-spec-kit} used 165 lines of check logic and received the highest clarity grade on all twelve specimens. Its scenarios kept the dialogue and its checks together, so the tested behaviour was visible in one place. By contrast, metric-oriented implementations often needed extra trace parsing, evaluator classes, or test-case setup. DeepEval and Pydantic Evals required 496 and 532 lines respectively.

The same study also showed a difference in diagnostic quality. Failed built-in checks in \emph{agent-spec-kit} usually identified the broken assertion, its location, and the expected and actual values. Several reimplementations reported only an \texttt{AssertionError}, a zero score, or a broad natural-language explanation. The structured counterexamples were therefore more useful for locating the exact tool, field, or state fact that failed.

The fault-injection study tested whether these checks detect regressions. On task-and-lane pairs that passed before injection, full-oracle scenarios caught most ordering and argument-binding faults. They also detected unwanted side effects that narrower lanes missed. This confirmed that combining reply, trace, and state checks gives stronger protection than testing any one surface alone.

The discovery studies then moved beyond fixed scripts. Simulated users and mutation fuzzing reached tool paths and failure signatures that did not appear in the manual conversations. This showed that the generative methods were not only producing different wording; they were exposing new behaviours. Manual scripts still provided a stable baseline against which these additional findings could be measured. Regression extraction converted the discovered failures into permanent scenario files using the same oracles, allowing findings from exploration to become repeatable tests.

Overall, the evaluation supports the main claim of the project. Multi-surface scenarios revealed failures that answer grading missed. The scenario language also made those checks easier to read and gave more precise failure reports than the compared implementations. Simulation and fuzzing added further value by finding failures outside the manually written paths.

\subsection{Limitations}
\label{sec:evaluation-limitations}

Authoring-clarity and failure-message grades in the expressiveness study relied on LLM judges at full scale rather than human evaluators. Those rankings and specificity scores may not match what human review would find. Only one reference agent and one telecom domain were studied, so the figures describe this setup rather than customer-support agents in general. LLM criteria in output and full lanes make some failures judge-dependent. Regression extraction generated a valid file for every eligible failure, but fewer than half of extracted scenarios reproduced the exact same assertion on immediate rerun. With user lines fixed, tool ordering and reply wording could still vary, so a different check broke first or the run passed outright.
