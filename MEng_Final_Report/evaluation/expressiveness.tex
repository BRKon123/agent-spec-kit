Promptfoo remains among the more concise ports (126 lines). Checks are mostly declarative \texttt{assert} entries in \texttt{promptfooconfig.yaml}, with trajectory rules expressed as compact assertion types rather than imperative trace code. The LOC measure counts only the body of each check (trace extraction, evaluator or metric configuration, and result capture) and excludes harness code outside the marked region. Totals therefore rise when a library expects the same plumbing repeated in every specimen. Trace normalisation, metric construction, and result capture each add lines even when the policy under test is simple. Metric-oriented libraries (LangSmith, Ragas, DeepEval, Pydantic Evals, Braintrust) occupy the upper half of Table~\ref{tab:expressiveness-loc} at roughly two to three times the line count of the declarative band. Authors must configure evaluators and map trace fields into library schemas in every specimen, and readers must chase that wiring before the policy under test becomes visible. \emph{agent-spec-kit} totals 165 lines and stays in the concise band because its scenario DSL states the whole check (stimulus, tool expectations, and assertions) in one contiguous block. A reader can follow a specimen from user script to oracle without adapters, sidecar configs, or per-specimen metric boilerplate.

Plain pytest reaches a similar total (167 lines) only by reintroducing the same trace-walking and field-guard patterns in nearly every check body. \emph{agent-spec-kit} therefore matches pytest on raw line count while doing more per line. Composable matchers replace bespoke guards, and the shared scenario vocabulary carries across all twelve specimens rather than twelve slightly different ad-hoc scripts. The extra bulk in metric-oriented ports is not cosmetic. It reflects real authoring effort and slower first-read comprehension, even when much of the gap is where code lives rather than how much policy logic each check expresses. The clarity study below judges readability directly. On a first read, is the \emph{intent} of each check obvious, or do you have to trace through helper code and framework wiring before you see what is being tested? Table~\ref{tab:expressiveness-authoring-clarity} and the listings that follow compare frameworks on that question specimen by specimen.

\subsection{Authoring clarity}

This study asks how easy that same check logic is to read, whether the test intent is obvious, whether you can see what the agent was told, and whether tools and fields under test are clear. For LOC and for clarity we use only the body of each check (the lines between marked start and end points in each implementation file), so helper code and imports are not counted. Grades were initially assigned by human judges on a pilot subset. An LLM (\texttt{openai:gpt-5-mini}) produced similar rankings, so the full table uses LLM grading as a more scalable, time and cost efficient way to run the study. The model assigns one combined A--D clarity grade per check and framework (Table~\ref{tab:authoring-clarity-rubric}, Table~\ref{tab:expressiveness-authoring-clarity}). Letter grades are \textbf{A best, D worst}. Clarity is separate from LOC and from failure-specificity (Table~\ref{tab:specificity-rubric}), which judges \emph{failure messages} only.

\subsubsection{Illustrative contrast for structured object shape (C02)}

Listing~\ref{lst:c02-clarity-contrast} contrasts three \emph{ways} of stating the same C02 policy across different libraries (structured specialist result). The specimens are a scenario specification, imperative trace inspection, and declarative eval-config assertions. The clarity study rewards how quickly a maintainer understands the policy when \emph{reading} the check, not whether the logic is equivalent after working through every step.

Specimen C02 requires \texttt{run\_network\_diagnostics\_specialist.result} to contain exactly \texttt{severity}, \texttt{recommended\_action}, and \texttt{escalation\_reason}, with values \texttt{high}, \texttt{create\_ticket}, and a non-empty reason. The same rule can be written as (i)~a scenario block that ties a user turn to an expected tool \texttt{result} object, (ii)~Python that finds the tool in a saved trace and checks each field, or (iii)~Promptfoo YAML that picks out the specialist result and applies an \texttt{is-json} schema. LangSmith and Pydantic Evals follow the same idea in code. Promptfoo works well when a built-in assert type fits. Otherwise custom logic (finding the right tool, conditional fields, nested children) has to live in JavaScript inside the YAML, which is harder to write and review than keeping checks in one place.

\begin{lstlisting}[caption={C02 structured object: scenario DSL, imperative pytest, and Promptfoo config (grades in Table~\ref{tab:expressiveness-authoring-clarity}).},label=lst:c02-clarity-contrast]
+------------------------ agent_spec_kit (C02)  grade A -------------------------+
(
    s.user_message("check")
    .assert_tool_calls(
        [
            m.tool_call(
                "run_network_diagnostics_specialist",
                result=m.object(
                    {
                        "severity": m.one_of("high"),
                        "recommended_action": m.one_of("create_ticket"),
                        "escalation_reason": m.string(min_len=1),
                    },
                    extra="forbid",
                ),
            ),
        ],
        ordered=True,
        allow_extras=True,
    )
)
+--------------------------------------------------------------------------------+
+------------------------- pytest_plain (C02)  grade B --------------------------+
tool = find_tool(walk_root_tools(trace), "run_network_diagnostics_specialist")
if tool is None:
    assert False
r = tool.get("result")
if not isinstance(r, dict):
    assert False
keys = set(r.keys())
if keys != _C02_REQUIRED_KEYS:
    assert False
ok = (
    r.get("severity") == "high"
    and r.get("recommended_action") == "create_ticket"
    and len(str(r.get("escalation_reason", ""))) >= 1
)
assert ok
+--------------------------------------------------------------------------------+
+--------------------------- promptfoo (C02)  grade B ---------------------------+
  - vars: {check_id: C02}
    options:
      transform: |
        (() => {
          const trace = JSON.parse(output);
          const t = (trace.tools || []).find(
            (x) => x.name === 'run_network_diagnostics_specialist');
          return JSON.stringify(t?.result ?? null);
        })()
    assert:
      - type: is-json
        value:
          type: object
          additionalProperties: false
          required: [severity, recommended_action, escalation_reason]
          properties:
            severity: { const: high }
            recommended_action: { const: create_ticket }
            escalation_reason: { type: string, minLength: 1 }
+--------------------------------------------------------------------------------+
\end{lstlisting}

Notice how the \emph{agent-spec-kit} excerpt reads like a short script. The opening \texttt{user\_message} and the tool-result check follow one another in the same block, so you can read the specimen top to bottom as a coherent story of what the customer says and what must hold in the trace. Pytest and Promptfoo split that story across trace-walking code, transforms, and schema assertions in separate places, so a reader has to jump between files and code paths before seeing what is being tested.

In Table~\ref{tab:expressiveness-authoring-clarity}, only the \emph{agent-spec-kit} implementation scores \textbf{A} on every specimen. The user turn and every field constraint appear in one declarative matcher block. Pytest and the metric-oriented libraries score mostly \textbf{B}. Trace parsing and evaluator wiring are visible in the graded excerpt. Pydantic Evals, Promptfoo, and Braintrust drop to \textbf{C} on a few specimens that assert over tool calls and arguments, where span queries or YAML transforms obscure the policy. Ragas and DeepEval reach \textbf{B} on several checks when custom metric bodies name the violated rule in plain text.

\emph{agent-spec-kit} scores \textbf{A} on eleven of twelve specimens and \textbf{B} on final-state only. Failures routinely name the check, where it ran in the dialogue, a JSON path, and expected-vs-actual witnesses. On tool checks the \texttt{Expected} block renders the scenario spec in focused form (Section~\ref{sec:matcher-spec-repr}). Plain pytest is almost always \textbf{D} on checks over tool calls and arguments (bare \texttt{AssertionError}) and only reaches \textbf{B} when authors hand-write a field-level message (C07). LangSmith, Pydantic Evals, Promptfoo, Braintrust, Ragas, and DeepEval cluster at \textbf{B} or \textbf{C}. They identify the rule, field, or metric but rarely expose structured counterexamples. Ragas \texttt{ToolCallAccuracy} on C07 returns only a scalar score (\textbf{C}). DeepEval \texttt{ToolCorrectnessMetric} and \texttt{JsonCorrectnessMetric} surface longer natural-language reasons (\textbf{B}) when checks fail.
