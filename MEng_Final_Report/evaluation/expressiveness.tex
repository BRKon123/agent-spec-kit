Promptfoo is the most concise overall (100 lines): checks are mostly declarative \texttt{assert} entries in a shared \texttt{promptfooconfig.yaml}, with trajectory rules expressed as compact assertion types rather than imperative loops. That compactness comes with indirection: policy for a specimen may sit in the YAML block, a \texttt{transform} that extracts the right tool result, and a Python provider that materialises the trace, so a maintainer often hops between files to see the full check. Several trace-heavy specimens (C02--C04, C08) are shortest under Promptfoo for that reason.

Plain pytest is also lean (113 lines total) on simple tool rules, but grows on structured-object and multi-turn specimens where authors spell out trace walking and field guards explicitly. Pydantic Evals totals the most lines (169), concentrated in conditional and multi-turn cases. \emph{agent-spec-kit} totals 160 and sits in the same band as LangSmith and Braintrust, only modestly above pytest and Promptfoo. That gap is smaller than it looks because each \emph{agent-spec-kit} specimen counts the whole scenario in one block, from customer turns through tool, output, and state checks, whereas the other implementations usually count only the assertion or scorer body and leave the surrounding harness in helpers or separate files. The higher \emph{agent-spec-kit} total is therefore mostly consolidation into one readable specification, not a large increase in policy per specimen; many individual checks are still only a few lines, including simple rules such as forbidding a tool call. Line count alone therefore understates how easy checks are to maintain when much of the apparent difference is where the code lives, not how much logic each check requires. The clarity study below judges readability directly: on a first read, is the \emph{intent} of each check obvious, or do you have to trace through helper code and framework wiring before you see what is being tested? Table~\ref{tab:expressiveness-authoring-clarity} and the listings that follow compare frameworks on that question specimen by specimen.

\subsubsection{Illustrative contrast: structured object shape (C02)}

Listing~\ref{lst:c02-clarity-contrast} contrasts three \emph{ways} of stating the same C02 policy across different libraries (structured specialist result): a scenario specification, imperative trace inspection, and declarative eval-config assertions. The clarity study rewards how quickly a maintainer understands the policy when \emph{reading} the check, not whether the logic is equivalent after working through every step.

Specimen C02 requires \texttt{run\_network\_diagnostics\_specialist.result} to contain exactly \texttt{severity}, \texttt{recommended\_action}, and \texttt{escalation\_reason}, with values \texttt{high}, \texttt{create\_ticket}, and a non-empty reason. The same rule can be written as (i)~a scenario block that ties a user turn to an expected tool \texttt{result} object, (ii)~Python that finds the tool in a saved trace and checks each field, or (iii)~Promptfoo YAML that picks out the specialist result and applies an \texttt{is-json} schema. LangSmith and Pydantic Evals follow the same idea in code. Promptfoo works well when a built-in assert type fits; otherwise custom logic (finding the right tool, conditional fields, nested children) has to live in JavaScript inside the YAML, which is harder to write and review than keeping checks in one place.

\begin{lstlisting}[caption={C02 structured object: scenario DSL, imperative pytest, and Promptfoo config (grades in Table~\ref{tab:expressiveness-authoring-clarity}).},label=lst:c02-clarity-contrast]
+------------------------ agent_spec_kit (C02)  grade A -------------------------+
| (
|     s.user_message("check")
|     .assert_tool_calls(
|         [
|             m.tool_call(
|                 "run_network_diagnostics_specialist",
|                 result=m.object(
|                     {
|                         "severity": m.one_of("high"),
|                         "recommended_action": m.one_of("create_ticket"),
|                         "escalation_reason": m.string(min_len=1),
|                     },
|                     extra="forbid",
|                 ),
|             ),
|         ],
|         ordered=True,
|         allow_extras=True,
|     )
| )
+--------------------------------------------------------------------------------+
+------------------------- pytest_plain (C02)  grade B --------------------------+
| tool = find_tool(walk_root_tools(trace), "run_network_diagnostics_specialist")
| if tool is None:
|     assert False
| r = tool.get("result")
| if not isinstance(r, dict):
|     assert False
| keys = set(r.keys())
| if keys != _C02_REQUIRED_KEYS:
|     assert False
| ok = (
|     r.get("severity") == "high"
|     and r.get("recommended_action") == "create_ticket"
|     and len(str(r.get("escalation_reason", ""))) >= 1
| )
| assert ok
+--------------------------------------------------------------------------------+
+--------------------------- promptfoo (C02)  grade B ---------------------------+
|   - vars: {check_id: C02}                                                      |
|     options:                                                                   |
|       transform: |                                                             |
|         (() => {                                                               |
|           const trace = JSON.parse(output);                                    |
|           const t = (trace.tools || []).find(                                  |
|             (x) => x.name === 'run_network_diagnostics_specialist');          |
|           return JSON.stringify(t?.result ?? null);                            |
|         })()                                                                   |
|     assert:                                                                    |
|       - type: is-json                                                          |
|         value:                                                                 |
|           type: object                                                         |
|           additionalProperties: false                                          |
|           required: [severity, recommended_action, escalation_reason]        |
|           properties:                                                          |
|             severity: { const: high }                                          |
|             recommended_action: { const: create_ticket }                       |
|             escalation_reason: { type: string, minLength: 1 }                  |
+--------------------------------------------------------------------------------+
\end{lstlisting}

Notice how the \emph{agent-spec-kit} excerpt reads like a short script: the opening \texttt{user\_message} and the tool-result check follow one another in the same block, so you can read the specimen top to bottom as a coherent story of what the customer says and what must hold in the trace. Pytest and Promptfoo split that story across trace-walking code, transforms, and schema assertions in separate places, so a reader has to jump between files and code paths before seeing what is being tested.

In Table~\ref{tab:expressiveness-authoring-clarity}, only the \emph{agent-spec-kit} implementation scores \textbf{A} on C02: the user turn and every field constraint appear in one declarative matcher block. Pytest and Promptfoo both score \textbf{B}: pytest spells the policy as step-by-step guards on a trace; Promptfoo separates \emph{where to read} the result (a short script in the config) from \emph{what must hold} (the schema); compact here, but the graded lines still do not show what the agent was told, and the tool lookup already needs embedded JavaScript. On other specimens (e.g.\ C03 conditional billing, C09 nested children), the whole check is a \texttt{javascript} block because YAML has no ready-made assert; low LOC can hide how awkward that is. Pydantic Evals, LangSmith, and Braintrust also score \textbf{B} on C02. Promptfoo has the fewest lines for this check when \texttt{is-json} suffices; that advantage disappears when policy must be scripted by hand.

\emph{agent-spec-kit} scores \textbf{A} on eleven of twelve specimens and \textbf{B} on final-state only: failures routinely name the check, where it ran in the dialogue, a JSON path, and expected-vs-actual witnesses. Plain pytest is almost always \textbf{D} on trace-heavy checks (bare \texttt{AssertionError}) and only reaches \textbf{B} when authors hand-write a field-level message (C07). LangSmith, Pydantic Evals, Promptfoo, and Braintrust cluster at \textbf{B} or \textbf{C}: they identify the rule or scorer but rarely expose structured counterexamples.
