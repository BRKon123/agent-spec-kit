\section{Fault detection across oracle lanes}
\label{sec:fault-detection}

The third study injects known faulty behaviour into the reference agent and measures whether the existing TelcoSupportBench oracles fail on those runs. The expectation is that more encompassing checks catch more injections: trace and state oracles can surface tool and store mistakes that still leave the customer-facing reply acceptable, whereas output-only grading may pass. We therefore track detection separately across the four oracle lanes from Section~\ref{sec:telcosupportbench}: output (O), state (S), trace (T), and full (F), which combines all three surfaces on the same scripted dialogue.

Ten fault families (F01--F10) reuse the same policy checks as the baseline bench, but run against a \emph{mutated} reference agent. Most mutations are prompt overrides that steer the coordinator toward a known bad habit; a few families (notably F04 and F07) also insert deterministic tool or reply probes so the fault is reproducible without relying on sampling alone.

\begin{description}
\item[F01 Premature escalation.] Opens a ticket or escalates before required troubleshooting steps (\texttt{send\_troubleshooting\_step}, diagnostics, or similar) when the user pushes for speed.
\item[F02 Wrong line / customer binding.] Uses a decoy \texttt{line\_id} (e.g.\ \texttt{LINE-WRONG}) or keeps the first line mentioned after the user corrects it; tool args and store mutations can bind to the wrong line.
\item[F03 Unsupported credit.] Calls \texttt{apply\_bill\_credit} even when \texttt{run\_billing\_policy\_specialist} returned ineligible.
\item[F04 Auth / privacy leak.] Reads account data before \texttt{authenticate\_customer}, or echoes PII in the reply while still unauthenticated.
\item[F05 Nested tool order.] Calls the network specialist's child tools in the wrong order or skips expected children under \texttt{run\_network\_diagnostics\_specialist}.
\item[F06 Structured output.] Violates conditional shape on specialist JSON (e.g.\ \texttt{amount} present when not eligible, or forbidden extra fields).
\item[F07 Missing clarification.] Places a ticket, SIM order, or credit while the user's line or intent is still ambiguous, instead of asking a clarifying question first.
\item[F08 Missing audit note.] Performs a sensitive mutation but omits the \texttt{add\_audit\_note} call the reference scenario requires.
\item[F09 Failure to act.] Explains helpfully yet refuses required mutations (\texttt{create\_support\_ticket}, \texttt{order\_replacement\_sim}, credits) when policy demands action.
\item[F10 Wrong issue binding.] After the user corrects the problem type, keeps the first ticket reason, specialist path, or line binding from the opening turn.
\end{description}

Each fault family is run only on combinations of a benchmark task and an oracle lane (for example, task T46 under the state lane S) where that same combination had already passed on the unmutated agent (Table~\ref{tab:baseline-initial}), so results are not confounded with failures the reference agent already exhibited. \emph{Detection} means that, after fault injection, the scenario fails the same checks that had passed before mutation. In Table~\ref{tab:fault-detection-summary}, the denominator (\emph{eligible}) counts how many such task-and-lane combinations in that cell passed on the baseline run; the numerator (\emph{detected}) counts how many of those same combinations fail after injection. A higher percentage is better: the oracle caught the fault on more of the baseline-passing runs in that cell. The matrix contains 152 such combinations from the primary run.

\paragraph{Worked example (F02 stale line binding, task T46).}
Task T46 is a multi-turn ticket flow: the user first asks for a ticket on \texttt{LINE-WRONG}, then corrects to the real work line \texttt{LINE-0046}. The \texttt{fault\_stale\_belief} mutant keeps binding mutations to the first line mentioned. The state oracle uses the same store check as the baseline task (\texttt{assert\_ticket\_for\_line(LINE-0046)}). After the dialogue the assistant claims a ticket on \texttt{LINE-0046}, but the store has no ticket on that line because the mutation stayed on the stale binding. Listing~\ref{lst:fault-detection-trace} shows the resulting state-lane panel (S oracle; F02 is detected on all three T46 lanes in Table~\ref{tab:fault-detection-summary}).

\subsection{Diagnostic quality when faults are detected}
\label{sec:diagnostic-quality-faults}

Detection alone does not tell a developer how to fix a run. For injections that \emph{were} caught on the full oracle (F lane), we replay the same policy checks in six evaluation-library implementations and grade the captured failure panels with the specimen rubric (Table~\ref{tab:specificity-rubric}, Section~\ref{sec:expressiveness}). Grades come from \texttt{openai:gpt-5-mini}; the Req/Where/E-vs-A columns are deterministic parity flags against the built-in oracle witness.

Together, lane detection rates and these diagnostic grades treat split oracles as complementary witnesses on the same policy, not redundant pass/fail signals.
