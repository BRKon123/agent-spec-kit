\section{Generative discovery studies}
\label{sec:generative-studies}

The fourth part of the evaluation asks whether layered discovery (manual scripts, simulated users, and mutation fuzz) finds failures beyond fixed regression dialogues, using the same F-oracles throughout. Fourteen tasks overlap across the user-simulation and fuzz studies (T03, T04, T17, T20, T27, T29, T30, T35, T38, T42, T43, T44, T45, T49).

\subsection{User simulation}

\subsubsection{Simulation design}

The user-simulation arm keeps the same F-oracles and reference agent as the manual scripts, but replaces the fixed customer dialogue with an LLM-powered \texttt{simulate\_conversation} loop. For each of the fourteen study tasks, the simulation setup defines a short \emph{task intent} (what the customer is trying to achieve), a block of \emph{situational facts} drawn from the task seed (line id, postcode, beliefs such as a wrong line id on T43), and five \emph{personas}, not five scripts. Each persona is a seed with a name, conversational style, behaviour notes, a disclosure pattern, and a pressure level. The simulator prompt tells the model it is only the customer, must follow the persona, and may volunteer or withhold details according to \texttt{reveal\_upfront} versus \texttt{reveal\_when\_prompted}.

Table~\ref{tab:persona-dimensions} summarises the persona fields. Disclosure upfront means the customer states relevant ids and context in early messages. Disclosure when prompted means they lead with the problem and answer when the agent asks. Segments end when an LLM \texttt{sim\_stop} judge (same model as the user) decides the task-specific stopping criteria are met (for example authentication completed and the agent has addressed the stated goal) rather than always exhausting a turn cap.

Personas are task-specific because the intent differs. On T42 (issue shift from data to SIM), seeds include \texttt{multi\_issue\_user}, who mentions several problems before prioritising data, and \texttt{late\_realisation\_user}, who changes the issue mid-thread. On T43 (wrong then corrected line), seeds include \texttt{simple\_correction} and \texttt{work\_personal\_mix\_up}. On T45 (delayed authentication), seeds include \texttt{impatient\_user} and \texttt{suspicious\_user}, who resist sharing a verification token early. The model chooses wording and turn boundaries. It does not replay the fixed lines of the manual script verbatim.

The second row in the table is a sensitivity check that holds conversation count at fourteen by taking only the first seed per task. Simulated users still reach fourteen unique paths and five signatures versus eleven paths and four signatures for manual scripts, so the path and signature advantage is not only an artefact of running more personas. The trade-off is clear. A simulation setup costs less authoring effort than a full manual script. The developer defines task intent, situational facts, and persona seeds rather than writing every customer line. Personas buy broader coverage and dialogue diversity because the user model chooses wording and turn shape. Manual scripts remain the stable regression backbone because their user lines are fixed and the same scenario always replays the same transcript. Simulated runs are stochastic. Rerunning the same persona can produce a different conversation, so a failure found in exploration is harder to pin as a permanent regression until it is extracted or rewritten with concrete user messages.

Across the study, simulation produced sixteen distinct failure signatures (Table~\ref{tab:user-sim-primary}), fifteen absent from manual-script failures. No invalid simulations were recorded. For example, manual T04 follows authentication, diagnostics, heartbeat, and ticket creation in a fixed order. Simulated T43 with a ``simple correction'' persona interleaves outage checks, duplicate \texttt{get\_line\_status}, diagnostics, and ticket creation in a different shape.

\subsection{Mutation fuzzing and failure taxonomy}

\subsubsection{Fuzzing design}

The fuzz arm does not invent new personas. It starts from the \emph{manual seed transcript} for each task (the canonical scripted dialogue), then applies one mutation operator per fuzz trial. Each of the fourteen tasks runs five trials. Each trial uses a named operator from Table~\ref{tab:fuzz-operators} with a fixed random seed for reproducibility. Operators are generic and reused across all fourteen tasks. Each trial applies one named operator to that task's manual seed transcript.

Each operator can be applied either as a deterministic transform over the seed lines (regex deletion, string replacement, reordering, template insertion) or as an LLM-guided mutation that realises the same named intent on the transcript, optionally conditioned on prior turns in multi-segment dialogues.

Table~\ref{tab:fuzz-operators} lists the operator catalogue and what each one does to the seed lines. Some operators are \emph{dynamic}. They depend on dialogue segment (for example \texttt{contradict\_entity\_later} appends a correction only after the first segment). A few trials compose two operators in sequence (for example \texttt{contradict\_entity\_later} followed by \texttt{ambiguous\_acknowledgement}).

Simulation and fuzz share two failure signatures, while fourteen simulation signatures and six fuzz signatures remain arm-specific. The arms remain complementary at the transcript level. Personas explore alternative customer \emph{styles} (tone, disclosure timing, pressure) that rewrite the dialogue around a task intent, whereas mutation operators perturb the fixed initial manual messages along named axes such as missing facts, entity swaps, or vague acknowledgements. A failure on T42 from a multi-issue persona (state oracle, ticket opened too early) does not recur under \texttt{interleave\_secondary\_intent} (fuzz strategy) on those messages. Conversely, T45 \texttt{drop\_required\_fact} (fuzz strategy) surfaces tool non-invocation when credentials are stripped from the script, a path simulation personas hit through different output-oracle wording. The implication for evaluation design is that neither arm subsumes the other. Simulation widens \emph{who} the customer might be, fuzz widens \emph{how} a plausible script might vary, and keeping both layers in the suite catches complementary regressions, including ones that share an oracle family but arise from different customer wordings.

\subsubsection{Why generative discovery matters}

Taken together, the user-simulation and fuzz studies widen coverage well beyond what a single manual script per task can exercise. On the fourteen shared tasks, simulated users ran seventy conversations and reached fifty-six unique tool paths and sixteen distinct failure signatures, against eleven paths and four signatures for manual scripts alone. Mutation fuzz added a further forty paths and eight signatures from seventy trials at the same median length. The combined study recorded sixty-one failing conversations (four manual, thirty-two simulation, twenty-five fuzz; Table~\ref{tab:failure-taxonomy}).

That breadth matters because real customers do not follow one canonical dialogue. They withhold credentials, correct themselves mid-thread, mix several issues, or answer in fragments. Personas and mutation operators surface tool orderings, binding mistakes, and policy violations that a test author is unlikely to script exhaustively, yet are exactly the stresses that matter in production-like settings where user behaviour is unpredictable. The case studies above (T42 simulation, T45 fuzz) illustrate failures that manual seeds did not expose in this run.

Generative search is only half the loop. Each failure is reported as a structured counterexample (check kind, path, turn, event trace) in the CLI and web UI (Section~\ref{sec:execution-workflow}), so a developer can see which expectation broke without reconstructing the episode from logs. Rerunning under a new experiment name and comparing pass/fail across scenarios supports the spec, run, inspect, and fix workflow. The next subsection on regression extraction enables this loop. When a simulated failure is worth keeping, extraction pins the realised transcript as a permanent regression script.

\subsection{Regression extraction from simulated failures}

\subsubsection{Extraction design}

Discovery becomes more useful when a surprising sim failure can be pinned as a permanent script. The regression-extraction arm takes failing user-simulation runs from twelve study tasks (T04, T17, T20, T27, T29, T30, T35, T38, T42, T43, T45, T49) with five persona seeds each, captures the realised customer transcript per generative step, and materialises it into a new \texttt{@scenario} in a regression module. The AST pass keeps the original F-oracle assertions and replaces \texttt{simulate\_conversation} with concrete \texttt{user\_message} lines from the captured run (Section~\ref{sec:generative}, Listing~\ref{lst:extracted-regression}). Each extracted test is tagged with a \texttt{regression\_id} (for example \texttt{REG-SIM-T29-1}) and keyed to the source \texttt{failure\_signature} so a rerun can be checked for the same assertion failure, not merely any failure.

\subsubsection{Study results}

Of sixty simulated conversations in this arm, twenty-nine failed and twenty-eight had transcripts captured successfully (one capture failed). All twenty-eight were written to \texttt{all\_regressions.py} with valid Python syntax and discoverable scenario functions (one hundred per cent import and collection success). Table~\ref{tab:regression-extraction} summarises the pipeline.

On immediate rerun, thirteen extracted scenarios failed again on the same check and JSON path as the original sim run (Table~\ref{tab:regression-extraction}). Only three passed outright (all on T04), giving a regression pass rate of 10.7\%. For tests extracted \emph{from} failures, a low pass rate is desirable because it means the pinned script still exercises the oracle rather than letting the agent slip through. The other twenty-five reruns failed. Nine broke on a different \emph{check kind} (for example an original \texttt{forbid\_tool\_calls} violation surfacing instead as an \texttt{assert\_output} judge failure), and three more on the same check type but at a different trace path after a slightly different tool ordering. The honest reading is mixed. Extraction reliably turns a stochastic dialogue into a readable, version-controlled script with the full F-oracle attached, but under half of extracted cases immediately reproduce the \emph{same} failure signature. That gap is expected because the agent remains stochastic even when user lines are fixed, and because each extracted scenario still carries the full multi-oracle F-check. Small differences in tool ordering or reply wording can shift which assertion breaks first even when the underlying policy stress is similar. Even when rerun behaviour drifts, the extracted file still documents the customer lines and policy checks that triggered the original discovery and can be edited or repeated like any other manual script.

\subsubsection{Illustrative extracted regression (T29)}

Listing~\ref{lst:t29-regression} shows an extracted regression for T29 (replacement SIM on the wrong line). The simulator produced one customer turn naming both \texttt{LINE-0029} and \texttt{LINE-WRONG}. Extraction materialises that line verbatim and keeps the trace and output oracles from the sim scenario. On rerun this case failed on the same forbidden early \texttt{order\_replacement\_sim} call as the initial simulation run. It is an example of a stable trace-level failure that reproduces reliably.

\begin{lstlisting}[language=Python,caption={Extracted regression \texttt{REG-SIM-T29-1}: concrete user line plus original F-oracle.},label=lst:t29-regression]
@ek.scenario(regression_id='REG-SIM-T29-1', tags=('telecom', 'regression', 'user-sim'), ...)
async def regression_REG_SIM_T29_1(s, store_us_t29):
    (
        s.user_message("Hi, I'm customer CUST-029 with verification token 1990-29-15. "
                       "The line I need fixed is LINE-0029 (not LINE-WRONG); I need a "
                       "replacement SIM sent to my default address at E1 6AN.")
        .forbid_tool_calls([m.tool_call('order_replacement_sim')], ...)
        .assert_tool_calls(
            [
                m.tool_call('authenticate_customer'),
                m.tool_call('order_replacement_sim',
                            args={'line_id': 'LINE-0029'}),
            ],
            ...)
        .assert_output(m.llm_criteria(...), ...)
    )
\end{lstlisting}

The regression study completes the discovery-to-regression workflow described in Chapter~\ref{chap:methodology}. Simulated users widen search, counterexamples explain what broke, and extraction preserves the dialogue as a script the team can keep in the suite without re-running the user simulator.
